# 팀원 작업 가이드 — 대시보드에 기능 붙이기

> 대상: **클로드코드 프롬프트로만 작업하는 팀원**
> 목표: 각자 기능을 만들되, **메인 대시보드의 모양은 그대로 두고 "기능만"** 깔끔하게 붙이기

---

## 0. 가장 먼저 이해할 한 가지

지금까지는 각자 **대시보드 전체를 통째로 만들고**, 나중에 기능 부분만 떼어내 메인에 옮기려다 보니 충돌이 우려됐습니다.

하지만 이 프로젝트는 그렇게 할 필요가 없습니다. **대시보드의 "공통 틀"(왼쪽 사이드바·역할 탭·전체 레이아웃)은 이미 메인에 완성돼 있고**, 모든 기능 페이지는 자동으로 그 틀 안에 들어가도록 설계돼 있습니다.

```
app/dashboard/layout.tsx        ← 공통 틀 (사이드바 등). 이미 완성됨. 건드리지 않음.
  └─ app/dashboard/내기능/page.tsx   ← 내가 만드는 건 "이 한 폴더"뿐
```

즉, **나는 대시보드를 만들 필요가 없습니다. 내 "기능 폴더" 하나만 추가하면, 메인의 대시보드 틀이 알아서 똑같이 씌워집니다.** 모양이 저절로 통일되는 이유가 이것입니다.

---

## 1. 건드려도 되는 곳 / 절대 안 되는 곳

작업 전에 이 표를 꼭 기억하세요. **충돌의 90%는 "공통 영역"을 건드려서 생깁니다.**

### ✅ 내가 자유롭게 만드는 곳 (내 기능 폴더)

```
app/dashboard/내기능/page.tsx       ← 화면
app/dashboard/내기능/loading.tsx    ← 로딩 화면 (필수)
app/dashboard/내기능/error.tsx      ← 에러 화면 (필수)
app/dashboard/내기능/actions.ts     ← DB 처리 (Server Action)
```

이 폴더 안의 파일은 **나만 만지므로 충돌이 날 수 없습니다.** 마음껏 작업하세요.

### 🚫 절대 함부로 고치지 않는 곳 (공통 영역)

| 파일 | 무엇 | 왜 위험한가 |
|---|---|---|
| `components/dashboard/nav-chrome.tsx` | 왼쪽 사이드바 메뉴 | 모두가 같은 파일 → **충돌 1순위** (아래 3-2 규칙 준수) |
| `app/dashboard/layout.tsx` | 대시보드 공통 틀 | 모양이 깨짐 |
| `app/dashboard/page.tsx` | 대시보드 첫 화면 | 모두가 공유하는 메인 화면 |
| `components/ui/*` | 버튼·카드 등 공통 부품 | 다른 사람 화면까지 깨짐 |
| `lib/supabase/*`, `types/*` | DB 연결·공통 타입 | 전체가 영향받음 |

> 이 파일들을 꼭 고쳐야 한다면 **먼저 팀에 공유**하고, 한 명만 수정하세요.

---

## 2. 작업 시작 전 환경 세팅 (← 충돌을 막는 핵심 단계)

> **왜 중요한가:** 내 컴퓨터의 오래된 버전 위에서 작업하면, 나중에 합칠 때 "남이 바꾼 부분"과 "내가 바꾼 부분"이 부딪쳐 충돌이 납니다. 그래서 **작업을 시작할 때마다 항상 최신 메인을 먼저 받아와야** 합니다.

클로드코드에 아래 프롬프트를 **그대로 복사해서** 붙여넣으세요. (`내기능이름`은 영어로, 예: `classrooms`, `staff`, `parents`, `settings`)

```
지금부터 새 기능 작업을 시작할 거야. 다음을 순서대로 해줘:
1. 현재 내가 저장 안 한 변경사항이 있는지 git status로 확인해줘. 있으면 멈추고 나한테 알려줘.
2. main 브랜치로 이동해서 origin/main 최신 내용을 pull로 받아줘.
3. main에서 새 브랜치 "feature-내기능이름"을 만들고 그 브랜치로 이동해줘.
4. 마지막으로 현재 어떤 브랜치에 있는지, main과 차이가 없는 상태인지 확인해서 알려줘.
```

이걸 하면:
- 항상 **메인 대시보드가 완성된 최신 상태** 위에서 시작하고,
- 내 작업은 **별도 브랜치**에 담겨 남의 작업과 섞이지 않습니다.

> ⚠️ **하지 말 것:** main을 pull하지 않고 내 로컬 파일에서만 작업 → 나중에 합칠 때 충돌 폭탄. (조건 1-1에서 우려한 상황)

## 3. 기능 개발 프로세스 (4단계)

### 3-1. 내 기능 폴더만 만들기

클로드코드에 이렇게 요청하세요 (예시는 "반 관리" = `classrooms`):

```
app/dashboard/classrooms/ 폴더에 "반 관리" 기능을 만들어줘.
- page.tsx, loading.tsx, error.tsx, actions.ts 를 모두 만들어줘 (프로젝트 규칙)
- 화면 안의 내용만 만들고, 사이드바나 layout.tsx 같은 공통 틀은 절대 건드리지 마.
- DB 접근은 Server Action(actions.ts)에서만, 클라이언트 직접 쿼리 금지.
- 기존 app/dashboard/children/page.tsx 의 구조·스타일을 참고해서 톤을 맞춰줘.
- UI 텍스트는 한국어, shadcn/ui 컴포넌트와 lucide-react 아이콘을 써줘.
```

> 💡 **핵심:** "공통 틀은 건드리지 마"라고 매번 명시하세요. 이 한 줄이 충돌을 막습니다.

### 3-2. 사이드바 메뉴에 내 기능 한 줄 추가하기 (← 충돌 1순위 구간)

내 기능 페이지를 만들었으면, 왼쪽 메뉴에서 눌러 들어갈 수 있게 **딱 한 줄**을 추가해야 합니다. 이 파일(`nav-chrome.tsx`)은 **모두가 공유하므로 충돌이 가장 잘 나는 곳**입니다.

> **왜 충돌이 나는가:** 모두가 똑같은 main에서 가지를 칩니다. 그래서 "각자 알아서 맨 끝에 추가"하면, 사실은 **모두가 똑같은 한 지점(메뉴 배열의 끝)** 에 서로 다른 줄을 넣는 셈이라 충돌이 납니다. "내가 1번, 네가 2번" 약속을 해도, 내 가지에는 아직 남의 줄이 없어서 **그 아래에 놓을 수가 없습니다.**

#### ✅ 충돌을 없애는 핵심: "쓰는 순서"가 아니라 "합치는 순서"로 줄을 쌓는다

> **한 문장 규칙:** 메뉴 줄은 개발 중에 넣지 말고, **합치기 직전에 최신 main을 받은 뒤** 맨 끝에 한 줄 붙이고 **바로 합친다.**

이렇게 하면 먼저 합친 사람의 줄이 main에 들어가고, 다음 사람은 **그 줄이 이미 보이는 상태**에서 그 아래에 붙이므로 → 자연스럽게 "맨 끝부터 아래로 순차" 정렬되고 **충돌이 나지 않습니다.**

**팀 규칙 3줄:**
1. **메뉴 한 줄은 맨 마지막에 추가** — 기능 폴더를 다 만들고, **PR 올리기 직전에만**.
2. **추가 직전에 반드시 `git pull origin main`** — 그래야 앞사람 줄이 보이고, 그 아래에 붙일 수 있음.
3. **메뉴가 든 PR은 한 번에 한 명씩 merge** — 단톡방에 "저 메뉴 머지합니다" 한마디 하고 순서대로.

클로드코드에 이 프롬프트를 **그대로** 쓰세요:

```
이제 사이드바 메뉴에 내 기능을 연결할 거야. 충돌을 막기 위해 순서대로 해줘:
1. 먼저 git pull origin main 으로 최신 메인을 내 브랜치에 받아줘. (앞사람이 추가한 메뉴 줄을 가져오기 위함)
2. components/dashboard/nav-chrome.tsx 의 MENU 배열에서, 닫는 괄호 "];" 바로 위 = 가장 마지막 줄 아래에 내 메뉴 한 줄만 추가해줘. 각 항목은 이렇게 채워줘:
   - href: 내가 만든 기능 폴더 경로 그대로. (예: 내 폴더가 app/dashboard/classrooms 이면 href 도 "/dashboard/classrooms". 새 이름을 지어내지 말고 폴더명과 똑같이 맞춰줘.)
   - label: 사이드바에 보일 한국어 메뉴 이름. (예: "반 관리") 이 이름은 메뉴 글자일 뿐 아니라, 그 메뉴를 눌렀을 때 열리는 페이지의 제목(헤더)·설명과도 같은 맥락이 되도록 page.tsx 안에서도 동일하게 맞춰줘.
   - icon: 기능에 어울리는 lucide-react 아이콘으로 적절히 골라줘.
   - roles: 일단 ["teacher"] 로 고정해줘. (현재 데모는 교사 화면만 쓰기 때문) 다른 역할에도 보이게 하려면 그건 각 작업자가 나중에 직접 바꿀 거니까, 지금은 임의로 늘리지 마.
3. 기존 메뉴 줄은 순서도 내용도 절대 바꾸지 말고, 내 한 줄만 "맨 아래에" 붙여줘.
4. 끝나면 git status로 nav-chrome.tsx 한 줄만 바뀌었는지 보여줘.
```

**각 항목이 무슨 뜻인지 (사람용 설명):**
- **`href` = 주소** — 내가 만든 폴더 경로와 **반드시 똑같아야** 메뉴를 눌렀을 때 내 페이지로 들어갑니다. 폴더명을 `staff`로 만들었으면 href도 `/dashboard/staff`. (이름은 기능에 맞춰 영어로, 폴더명과 1:1로 맞추세요.)
- **`label` = 메뉴 이름** — 여기 적은 한국어가 **사이드바 글자**가 됩니다. 그리고 그 메뉴를 누르면 열리는 **페이지 제목·설명도 같은 이름**으로 맞춰두면, 메뉴와 화면이 따로 놀지 않고 한 덩어리처럼 보입니다. (그래서 프롬프트에 "page.tsx 안에서도 동일하게 맞춰줘"를 넣었습니다.)
- **`roles` = 누구에게 보일지** — 지금은 **데모라서 `["teacher"]`(교사)로 고정**합니다. 교사 화면만 시연할 예정이기 때문입니다. 원장·관리자 등 **다른 역할에게도 보이게 하고 싶다면, 그건 각 작업자가 본인 기능에 한해 직접 바꾸세요.** (가이드대로면 기본은 교사 고정)

> 이미 `classrooms` `staff` `parents` `settings` 메뉴는 **틀에 들어가 있습니다.** 이 4개 기능을 맡았다면 메뉴 추가는 생략하고 **페이지 폴더만** 만들면 됩니다. (단, 그 메뉴들의 기존 `roles`는 데모 고정값과 다를 수 있으니, 교사 화면만 쓸 거면 본인 메뉴 줄의 roles를 `["teacher"]`로 직접 맞추세요.)

### 3-3. 로컬에서 직접 눈으로 확인

```
npm run dev
```
실행 후 브라우저에서 내 기능 주소로 접속해 동작을 확인하세요:
- 예: `http://localhost:3000/dashboard/classrooms?role=director`
- 사이드바·상단 역할 탭이 **다른 기능과 똑같이** 보이면 성공입니다. (틀이 자동으로 씌워진 것)

### 3-4. 커밋 & 올리기 (← 멤버는 "PR 보내기"까지만!)

> **중요 — 역할 구분:** **멤버는 "내 브랜치 push + PR 생성"까지만** 합니다. PR은 main에 합치는 게 아니라 **"확인해 주세요"라고 팀장에게 보내는 알림(제안)**입니다. **실제 main 반영(머지)은 팀장이** 정상 동작을 확인한 뒤에 합니다. **멤버는 머지 버튼을 누르지 않습니다.**
>
> 즉, 여기서 말하는 push는 **"내 브랜치"를 올리는 것**이지 *"main에 올리는 것"이 아닙니다.* main은 멤버 손으로는 바뀌지 않습니다.

클로드코드에 이렇게 요청하세요:

```
지금까지 만든 내 기능을 커밋하고, 팀장 검토용 PR을 올릴 거야. main에는 직접 합치지 마.
1. git status로 바뀐 파일을 보여주고, 공통 파일(layout, ui 등)을 실수로 건드리지 않았는지 확인해줘.
2. 내 기능 폴더 파일들 + nav-chrome.tsx 한 줄 변경만 커밋해줘.
3. 커밋 메시지는 "feat: 반 관리 기능 추가" 형식으로 한국어로 써줘.
4. 내 feature 브랜치를 origin에 push해줘. (main이 아니라 내 브랜치에만 올리는 거야)
5. 내 브랜치 → main 방향의 PR을 만들어줘. 단, PR을 만들기만 하고 절대 머지하지는 마. 머지는 팀장이 할 거야.
6. 끝나면 PR 주소(링크)를 알려줘. 그 링크를 단톡방에 공유해서 팀장에게 검토 요청할 거야.
```

PR을 올렸다면 멤버의 작업은 **여기서 끝**입니다. 단톡방에 **"PR 올렸습니다. 검토 부탁드려요"** 라고 알리고 팀장의 확인을 기다리세요.

## 4. (팀장용) PR 검토하고 main에 합치기

> 이 4번은 **팀장이 하는 작업**입니다. 멤버는 안 해도 됩니다.

팀장은 멤버가 올린 PR을 받아서, 정상 동작을 확인한 뒤 **한 번에 하나씩** 머지합니다. (메뉴 줄 충돌을 막기 위해 동시에 두 개를 머지하지 않습니다.)

```
멤버가 올린 PR을 검토하고 main에 합치려고 해. (나는 팀장이야)
1. 이 PR이 바꾼 파일 목록을 보여줘. 내 기능 폴더 + nav-chrome.tsx 한 줄 외에 공통 파일을 건드리진 않았는지 확인해줘.
2. main 최신 상태와 충돌이 있는지 알려줘.
3. 충돌이 없으면 그대로 머지해줘.
4. 만약 사이드바 메뉴(nav-chrome.tsx)에서 충돌이 났다면 — 보통 여러 멤버가 메뉴 줄을 같은 자리에 추가해서 생긴 거야.
   → 먼저 main에 들어가 있던 줄을 위에 그대로 두고, "이 PR의 메뉴 줄을 그 아래로" 옮겨서 둘 다 살려줘. 어느 줄도 지우지 마.
5. 정리 후 npm run dev로 화면이 정상인지 확인하고 머지해줘.
```

> 메뉴 줄 충돌은 항상 **"먼저 온 줄 위 / 새 줄 아래"**로 쌓으면 끝입니다. 순서만 맞추면 되므로 클로드가 안전하게 처리할 수 있습니다.
>
> 💡 머지 순서를 단톡방에서 정해두면(예: "A → B → C 순서로 올려주세요") 팀장이 그 순서대로 머지하기만 하면 메뉴가 깔끔하게 위에서 아래로 쌓입니다.

---

## 5. 자주 하는 실수 체크리스트

작업 전/후에 스스로 점검하세요:

- [ ] 작업 시작할 때 **main을 pull로 먼저 받았다** (2번 단계)
- [ ] main이 아니라 **내 feature 브랜치**에서 작업하고 있다
- [ ] 내가 만든 건 **`app/dashboard/내기능/` 폴더**와, 필요 시 메뉴 **한 줄**뿐이다
- [ ] `layout.tsx`, `components/ui/*`, `lib/*` 같은 **공통 파일을 건드리지 않았다**
- [ ] `loading.tsx`, `error.tsx`를 **둘 다 만들었다** (프로젝트 필수 규칙)
- [ ] `npm run dev`로 **내 눈으로 화면을 확인했다**
- [ ] 커밋 전에 `git status`로 **엉뚱한 파일이 안 바뀌었는지 봤다**
- [ ] 내 일은 **PR 올리기까지** — **머지(main 반영)는 팀장이 한다** (멤버는 머지 버튼 누르지 않음)

---

## 6. 한 장 요약

```
[작업 시작]
  main pull  →  feature 브랜치 생성
        │
        ▼
[기능 개발]  app/dashboard/내기능/  폴더만 작성  (공통 틀은 안 건드림)
        │
        ▼
[확인]  npm run dev 로 눈으로 보기
        │
        ▼
[메뉴 연결]  ⚠️ PR 올리기 직전에:  git pull main → "내 한 줄"을 맨 아래에 붙이기
        │              (앞사람 줄 위 / 내 줄 아래로 쌓임 → 충돌 0)
        ▼
[제출(멤버)]  커밋 → 내 브랜치 push → PR 생성 → 단톡방에 "검토 부탁" 알림
        │        ※ 여기서 멤버 끝. main은 안 건드림. 머지 버튼 누르지 않음.
        ▼
[머지(팀장)]  PR 확인 → 한 번에 하나씩 머지 → 비로소 main 반영
                       (충돌 시 "먼저 온 줄 위 / 새 줄 아래"로 정리)
```

**기억할 두 문장:**
1. 나는 대시보드를 만들지 않는다. **내 기능 폴더 하나만** 만들면, 메인의 대시보드 틀이 알아서 똑같이 씌워진다.
2. 멤버는 **PR(검토 요청)까지**, **main 반영(머지)은 팀장**이 한다.
